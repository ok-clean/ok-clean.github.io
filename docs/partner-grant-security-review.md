# 업체 수동 배정·견적 권한 수명주기 — 에뮬레이터 전용

기준: PR #16 (e9a4b55122499b0032c4960c2d0424e62e7c9f92). 운영 Firebase 및 기존 홈페이지에는 적용하지 않는다.

## 코드 검토에서 확인한 빈틈

이전 시험 규칙은 승인 업체의 회사명·지역·전문분야 변경을 허용했고, 관리자가 미승인 업체에도 배정 문서를 만들 수 있었다. 배정된 업체의 견적 생성에는 예약확정/작업완료/종료·기한 경과 검사가 없었다. 승인 취소 후 재승인하면 남아 있던 배정 문서가 다시 유효해졌고, 업체 UID에 견적을 고정해 재배정 이력과 신규 견적을 구분할 수 없었다. 이는 시험 규칙 검토 결과이며 실운영 Firebase 취약점이라고 단정하지 않는다.

## 새 계약 (스키마 변경 — 자동 운영 마이그레이션 없음)

- `partner_profiles/{uid}`: 필수 `approvalVersion` 추가. 신규 검토중=0. 관리자의 상태 변경마다 정확히 1 증가. 승인된 프로필의 업체 자체 수정은 차단하며 명시적 재검토 전환 후 변경한다.
- `quote_requests/{id}/assignments/{uid}`: 현재 권한 포인터 `{grantId}`만 저장한다.
- `quote_requests/{id}/grants/{grantId}`: 배정 시점의 `partnerUid, approvalVersion, service, area, size, date, createdAt`만 저장한다. 이름·전화·원본 ownerUid·상세 주소는 허용하지 않는다.
- 포인터와 새 grant는 같은 트랜잭션/배치에서 생성되어야 한다. 규칙의 getAfter로 쌍방 일치를 확인한다. 과거 grant 재사용은 금지한다.
- `quote_requests/{id}/offers/{grantId}`: 배정별 생성 전용 견적. 승인 버전·현재 포인터·본인 인증·활성 요청·일정 확인을 모두 통과해야 조회/생성 가능하다.
- 승인 취소/재승인 또는 배정 해제 시 과거 grant는 접근 불가. 재배정은 새 grant와 새 견적을 만들며, 이전 기록은 관리자만 볼 수 있다.
- 예약확정·작업완료·종료 및 기한이 지난 요청은 업체 신규 견적과 조회를 차단한다. 예약 이후 작업 수행용 권한은 이 시제품에서 구현하지 않았다.

## 기능 코드

`partner-matching-service.cjs`: 관리자 승인 상태 변경, 원자적 수동 배정, 권한 포인터 해제, 업체 최소정보 조회, 견적 제출. Firebase **Web SDK**의 인증된 클라이언트를 사용하며 보안 판단은 Firestore 규칙에서 재검사한다. Firebase Admin SDK를 주입하는 서버용 서비스가 아니다. 화면과 실인증은 아직 연결하지 않았다.

## 검증 방식

- 기존 고객 요청 생성/입력/날짜/개인정보/관리자 전용 조회 회귀 검사를 보존하고 변경한 업체 스키마에만 테스트를 맞춘다.
- 새 `partner-matching.test.cjs`는 실 Firestore 에뮬레이터에서 가짜 인증·가짜 고객을 사용한다. 서비스 함수 우회 직접 쓰기, 동시 배정, 불완전한 배치, 승인 취소/재승인, 재배정, 타 업체 조회, 완료 후 견적, 기록 불변성을 검사한다.
- 로컬 Node 문법 검사를 수행했다. 컨테이너에서 GitHub/npm DNS 조회가 실패하여 로컬 에뮬레이터 검사는 실행하지 못했다. 실제 에뮬레이터·브라우저 결과는 GitHub Actions 결과를 기준으로 PR에 별도 기록한다.

## 운영 전 남은 조건

실제 업체 사업자 심사·관리자 계정 보안·관리자 승인 감사로그·고객 동의·배정 수 제한·스팸·분산 멱등성·예약 선택/취소·사진 및 보존/삭제는 별도 구현이 필요하다. 현재 원본 요청의 관리자 상태 변경은 기존 계약을 유지한다. 이 PR이 전체 예약 상태기계를 서버에 구현한 것은 아니다.

이전 프로필·배정·견적 스키마는 자동 변환하지 않는다. 버전이 없는 프로필은 권한을 부여하지 않는다. 운영 적용 전 기존 회원 규칙과 데이터 마이그레이션을 별도 검토해야 한다. 불변 기록은 영구 보존 정책이 아니며, 승인된 보유기간/삭제 작업을 신뢰할 수 있는 서버에 마련해야 한다. 접근 회수는 이후 서버 요청을 막는 것이지 업체가 이미 본 정보의 복사본까지 지우는 기능이 아니다.

PR #8의 Pages 시제품 배포 제외, #5→#12→#13→#14→#15→#16 의존 관계를 검토해야 한다. main 병합·운영 배포·유료 신청은 별도 승인 전 금지.
