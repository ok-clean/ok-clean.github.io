# 고객의 요청 상태 확인 — 가상 시제품

PR #24의 시험용 취소 흐름을 기반으로 한다. 실제 고객 화면·인증·서버·운영 Firebase에는 연결하지 않는다.

## 왜 별도 확인이 필요한가

기존 접수 확인의 `confirmed`는 요청이 접수된 사실을 뜻하며, 취소 여부나 현재 예약 상태를 보증하지 않는다. 취소 뒤에도 과거 요청 문서가 남으므로 기존 접수 확인만으로 취소 성공·실패를 판단하면 안 된다. 기존 연습 화면의 접수 확인 메시지에 취소 여부는 별도로 확인해야 한다는 안내를 덧붙였다.

## 최소 응답과 권한

본인 인증과 소유권을 확인한 가상 서버는 다음 상태 코드만 반환한다. 이름·연락처·업체정보·요청 식별자와 내부 오류는 응답에 포함하지 않는다.

| 저장된 요청 상태 | 상태 코드 | 의미 |
| --- | --- | --- |
| 신규·검토중·상담중 | processing | 조회 시점에 해당 상태로 기록됨 |
| 취소 | cancelled | 조회 시점에 취소 상태로 기록됨 |
| 예약확정 | booked | 조회 시점에 예약확정으로 기록됨 |
| 작업완료 | completed | 조회 시점에 작업완료로 기록됨 |
| 종료 | closed | 조회 시점에 종료로 기록됨. 취소로 단정하지 않음 |

`processing`은 희망일의 유효성이나 취소 요청 실패를 보증하지 않는다. 응답은 조회 순간의 스냅샷이며, 시간이 걸리는 취소 요청은 그 후에도 완료될 수 있다. 일시 오류·타임아웃은 성공 또는 실패로 오인하지 않는다. 사용자가 별도로 다시 확인할 수 있도록 안내하며 자동으로 취소 요청을 재전송하지 않는다.

없는 요청과 다른 사람의 요청은 동일한 응답이다. 익명·미검증 계정은 거부하고, 모르는 상태 값은 오류 처리한다. 고객 브라우저에는 원본 문서의 직접 읽기 권한을 주지 않는다. 신뢰 서버 시험용 리더는 실제로 원본 문서를 읽지만 소유권을 검사한 후 최소 상태만 반환한다. Firebase 보안 규칙은 문서의 특정 필드만 감출 수 없으므로 운영 권한을 별도로 설계해야 한다.

## 구현과 제한

- `request-state-handler.cjs`: 검증·요청 제한·읽기 함수를 주입받는 서버 시험 코드. 진짜 토큰 검증·폐기 확인과 분산 요청 제한은 미구현.
- `request-state-reader.cjs`: 에뮬레이터의 가상 관리자 Web SDK로 서버에서 읽는다. 운영 Admin SDK는 보안 규칙을 우회하므로 소유권·인증·상태 검증과 최소 IAM 권한이 별도로 필요하다.
- 정적 연습 화면은 가상 데이터와 `connect-src 'none'`만 사용한다. 서버 조회·실제 취소·로그인·예약·개인정보 저장에 연결되지 않는다. 브라우저 통합 검사는 Playwright의 시험용 함수 주입으로만 에뮬레이터의 가상 상태를 전달한다. 이는 HTTP 전송이나 실제 인증을 검증한 것이 아니다.
- 이후 HTTP 연결 전 HTTPS, 무캐시 응답, 제한, 취소 후 재조회와 인증 연속성, 취소가 실제 정보 삭제가 아니라는 안내가 필요하다. 기존 익명 신청과 검증 계정의 동일 UID 연결·분실 복구는 여전히 미구현이다.
- 고객·업체의 취소 알림, 예약 이후 취소 정책, 개인정보 보관·파기 및 실제 운영 환경 검증은 별도 작업이다. PR #8의 시제품 배포 제외를 검토하고 별도 승인 없이 main에 병합하거나 배포하지 않는다.

## 검증

가짜 데이터로 상태 전체 분기, 타인·없는 요청 동일 응답, 직접 문서 조회 거부, 오류와 민감정보 비노출, 취소 성공 후 상태 확인, 취소와 조회가 겹친 경우를 시험한다. 업체 견적 제출과 취소가 겹칠 때 먼저 확정된 기록은 남고 취소 후 새 접근은 차단되는지도 에뮬레이터에서 검사한다. 검사에서 결과가 불확실할 때의 후속 확인·명시적 사용자 재시도를 흉내 내더라도 조회 순간의 처리 중 상태만으로 취소 실패를 확정하지 않는다.
