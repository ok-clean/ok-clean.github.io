# 고객 접수 상태 조회: 서버 전용 시제품 (미배포)

대상: `prototype/security/receipt-status-handler.cjs`. 단위 테스트용 순수 함수이며 HTTP 서버, Firebase Admin SDK, 실제 고객 DB에 연결되지 않았습니다.

## 처리 계약

1. 서버에서 신뢰 가능한 Firebase Admin SDK로 ID 토큰의 서명·대상 프로젝트·만료 시간을 검증한 뒤 검증 결과만 콜백으로 전달합니다. **브라우저의 자체 인증 여부 표시나 임의 JSON을 신뢰하면 안 됩니다.**
2. 이메일이 실제 인증된 비밀번호 계정 또는 인증된 전화번호 계정만 조회를 요청할 수 있게 합니다. 익명·미인증 계정은 조회할 수 없습니다.
3. 접수 ID 형식을 확인하고, 검증된 UID별 서버 측 속도 제한을 적용한 뒤 본인 소유의 접수인지 대조합니다.
4. 본인 소유가 확인된 경우에도 응답에 `confirmed`만 포함하고 이름·전화번호·주소·원본 접수 정보를 포함하지 않습니다.
5. 타인 소유 요청과 존재하지 않는 요청은 같은 404/`unavailable` 응답을 보냅니다. 운영 오류의 상세 메시지나 개인 식별 정보는 응답에 포함하지 않습니다.

## 출시 전 해결할 선행 조건

- **가장 중요한 데이터 모델 문제:** PR #5의 신규 접수는 익명 UID를 `ownerUid`로 기록합니다. 이후 고객이 별도 확인된 계정으로 로그인하면 UID가 달라질 수 있습니다. 실서비스에서는 같은 Firebase 계정의 안전한 자격 연결, 또는 관리자가 확인한 서버 측 소유권 이전·증빙 기록 등 검증 가능한 흐름을 먼저 구현해야 합니다. 요청 ID나 전화번호만 알고 있다는 이유로 소유권을 부여하지 마세요.
- `verifyIdToken`, `loadRequest`, `enforceRateLimit`은 현재 전부 테스트 주입 콜백입니다. 실제 서버 구현, 서버 측 App Check/어뷰징 완화, 인증 전 IP 한도, 감사 로그의 개인정보 마스킹이 필요합니다.
- 이 코드를 브라우저에 관리자 권한으로 배포하지 마세요. 운영 Firestore 기존 회원 규칙을 덮어쓰지 마세요.
- API가 구현되더라도 실제 공개 전에 인증 계정 연결, 예외 흐름, 고객 본인 확인, 보유·삭제 정책, 기존 상담/회원 UX 및 모바일 접근성을 시험해야 합니다.
- 지금은 단순 접수 확인만 모델링합니다. 고객용 상세 상태 조회, 견적 비교, 예약/취소 및 결제 기능은 없습니다.
- 이 시제품은 무료/유료 서비스에 가입하거나 과금 설정을 바꾸지 않습니다.

## 안전 테스트

`node prototype/security/receipt-status-handler.test.cjs`

검증: 서명검증 콜백 실패, 익명·미인증 계정 차단, 올바른 본인 조회, 타인/미존재 동일 응답, 개인정보 미반환, 허용되지 않은 ID, 속도 제한, DB 오류 비노출, 전화 인증 계정 시뮬레이션. 전부 가상 데이터로 실행합니다.
