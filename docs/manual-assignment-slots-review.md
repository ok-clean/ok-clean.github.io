# 수동 매칭 배정 슬롯 — 에뮬레이터 시제품

이 문서는 테스트용 설계다. PR #18 및 선행 #17 등에 의존한다. 운영 Firebase 규칙으로 복사·배포하지 않는다. 최대 3개는 초기 사업 운영을 검토하기 위한 가정이며 실제 정책으로 확정된 수치가 아니다.

## 모델과 보안 경계

요청마다 slots/0, slots/1, slots/2 세 문서만 만들 수 있다. 각 슬롯에는 업체 UID와 grant ID만 포함한다. 새 배정은 슬롯, assignments/{업체 UID}, grants/{grantId}를 같은 트랜잭션에서 만들며 규칙이 세 문서의 상호 일치를 확인한다. 승인된 업체는 유효한 현재 배정일 때만 최소 요청 정보와 해당 견적에 접근한다. 고객 이름과 연락처는 슬롯·권한 문서에 없다.

같은 업체는 현재 포인터를 하나만 가진다. 슬롯과 포인터는 동시에 삭제해야 하며 다른 슬롯에는 영향을 주지 않는다. 재배정은 새 grant ID를 사용한다. 이미 발행된 grant와 견적은 에뮬레이터에서 관리자 기록으로 남는다. 접근 회수는 이미 본 정보의 복사본을 회수하지 않는다.

업체 승인 취소나 요청 종료는 조회 권한을 즉시 끊지만 슬롯 자체를 자동 삭제하지 않는다. 관리자가 배정을 해제해야 슬롯이 비워진다. 3개가 모두 점유된 동안 4번째 배정은 거부된다. 운영 시 자동 정리·사고 복구 정책은 별도 결정해야 한다.

## 테스트와 제한

가짜 고객·업체 계정과 Firestore 에뮬레이터에서 네 업체 동시 배정, 직접 쓰기 우회, 슬롯 단독 변경/삭제 거부, 승인 철회와 해제, 중복 해제 경쟁, 신규 grant로 재배정, 기존 권한·견적 회귀를 확인한다. PR의 Actions 실행 결과를 별도로 확인한다.

이것은 실제 업체 화면, 고객 비교, 예약·취소 상태 관리, 배정 이력 감사, 악용 방지, 개인정보 보존·삭제 또는 3자 동의 완성품이 아니다. 이전 슬롯 없는 포인터·grant는 새 코드에서 사용하거나 자동 전환하지 않는다. 운영 시 별도 마이그레이션과 검증이 필요하다. Firebase Admin SDK는 규칙을 우회하므로 신뢰 서버에도 제한·인증·원자성과 감사통제를 강제해야 한다. 운영 DB 데이터 변경이나 서비스 가입은 하지 않는다.
